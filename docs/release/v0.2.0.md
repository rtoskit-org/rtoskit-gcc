The toolchains now carry rtoskit-libc 0.6.0 and its new `fast` build, a faster maths library with a looser accuracy
contract. The compilers, the patches and the multilibs are the same as in v0.1.1; a project that builds with v0.1.1
builds unchanged, and uses `fast` only when you ask for it.

## Highlights

- **rtoskit-libc 0.6.0**, up from 0.5.3. The public headers and the ABI are those of 0.5.3, so a program built against
  the earlier toolchains links unchanged. The release also fixes accuracy defects in the strict maths library that the
  `release` and `speed` builds use (`pow`, `atanf`, `log1p`, `sin`, `cos`, `erf` and `lgamma`); they change results
  towards the correctly rounded one. See the
  [rtoskit-libc 0.6.0 release notes](https://github.com/rtoskit-org/rtoskit-libc/releases/tag/v0.6.0).
- **A third build of the library, `fast`**, installed for every multilib beside `release` and `speed`. It is the
  `speed` build with a different maths library: faster, accurate to nearest only (below 1 ulp, 1.5 ulp for `tan`,
  `tanf`, the hyperbolic functions and `erf`), and `sqrt` and `hypot` stay correctly rounded. rtoskit-libc measures its
  maths at a third to a nineteenth of the `release` build's instructions, depending on the core. Other rounding modes
  keep each result's sign, not its accuracy, so use `release` or `speed` where code changes the rounding mode. Code
  outside maths is the same as in `speed`.
- **`--fast`** links it, as `--speed` links the speed build:

  ```sh
  arm-none-eabi-gcc -mcpu=cortex-m4 -mfloat-abi=hard --fast main.c -lm
  ```

  A program links one build; do not combine `--fast` with `--speed`. rtoskit-libc's README has a section, *Choosing
  release, speed or fast*, with the contracts, code sizes and instruction counts per core.
- **GCC 16.2.0, 15.3.0 and 14.4.0**, each with GDB 17 and Python, for x86_64 Linux hosts, as in v0.1.1. Each archive is
  larger than before, by 22 to 33 MB, since it holds a third build of the library for every multilib.

## Good to know

- As before, the toolchains are **built and tested on the maintainer's machine**, not in CI. Each passed
  `tools/scripts/validate-toolchain` and rtoskit-libc's unit tests built against the installed toolchain, in the
  `release`, `speed` and `fast` builds on eight core options. GCC 16.2.0's C torture tests (`tools/scripts/gcc-torture`, for
  `-mcpu=cortex-m4 -mfloat-abi=hard`) ran for the first time: 24,439 passed and nothing failed that
  `tools/dejagnu/torture.xfail` does not expect (29 expected failures, 7 unresolved). They were not run on GCC 15.3.0
  and 14.4.0, or on other cores ([#18](https://github.com/rtoskit-org/rtoskit-gcc/issues/18)).
- `test-installed` now builds the library's fast-contract expectations (`fast/expect.c`, `fast/bounds.c`) in the `fast`
  build and checks that the installed headers are rtoskit-libc's own; the strict accuracy tests do not hold for `fast`.
- The known limitations of v0.1.1 stand: everything ran under `qemu-arm` through the Linux test port and the bare-metal
  `none` port has not run on a Cortex-M core ([#5](https://github.com/rtoskit-org/rtoskit-gcc/issues/5)); C++ has no
  wide characters and `std::filesystem` does nothing useful; the multilib set is a subset of GCC's `rmprofile` set
  ([#3](https://github.com/rtoskit-org/rtoskit-gcc/issues/3)).
- The archives carry no provenance attestation. Check them against `SHA256SUMS`; the tag is signed.

See the [README](https://github.com/rtoskit-org/rtoskit-gcc#readme) for the multilib table, the specs options and how to
build the toolchains yourself.
