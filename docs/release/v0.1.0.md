The first release of rtoskit-gcc: `arm-none-eabi` GCC cross toolchains for Cortex-M, built with
[crosstool-NG](https://github.com/crosstool-ng/crosstool-ng) on [rtoskit-libc](https://github.com/sgstreet/rtoskit-libc)
as the C library. This is a `0.x` pre-release: the multilib set, the specs options and the patches may still change
between minor releases.

## Highlights

- **Three GCC majors**, each at its newest minor: 16.2.0, 15.3.0 and 14.4.0, for x86_64 Linux hosts, each with GDB 17
  and Python.
- **rtoskit-libc 0.5.2** is the C library. It is built for every multilib in both its `release` (size) and `speed`
  builds, with `-funwind-tables -mpoke-function-name`, so a backtrace passes through library frames and each library
  function carries its name in the code before it.
- **Seven Cortex-M multilibs** (Armv6-M, Armv7-M, Armv7E-M with and without the single- or double-precision FPU, and
  Armv8-M Mainline), selected by the usual `-mcpu`, `-march` and `-mfloat-abi` options. The default, with no `-mcpu`, is
  Thumb Armv6S-M soft-float.
- **`local-exec` is the default TLS model**, which rtoskit-libc's `thread_local` needs. `-ftls-model=` on the command
  line still overrides it.
- **C and hosted C++.** `g++` builds with libstdc++ over rtoskit-libc's POSIX threads (`--enable-threads=posix`):
  exceptions, RTTI, `thread_local` destructors, `std::thread`, the mutex classes, `std::condition_variable`,
  `std::call_once`, `std::future`, `std::async`, `std::println`, `std::regex`, `std::ranges` and `std::chrono` work.
  `std::stacktrace` links with `-lstdc++exp`.
- **Link with `--specs=rtoskit.specs`.** It compiles with only rtoskit-libc's headers, links the library for the
  matching multilib, and leaves the startup code, linker script and heap bounds to you. `--speed`, `--libc=<variant>`
  and `--port=<name>` choose the speed build, a library variant and an RTOS port.

## Good to know

- The toolchains are **built and tested on the maintainer's machine**, not in CI. Each passed
  `tools/scripts/validate-toolchain` (multilibs, TLS, gdb Python, threaded C and C++ programs run under `qemu-arm`)
  and rtoskit-libc's unit tests built against the installed toolchain. The GCC C torture tests have not been run on
  these toolchains ([#18](https://github.com/sgstreet/rtoskit-gcc/issues/18)).
- Everything ran under `qemu-arm` through rtoskit-libc's Linux test port. The default bare-metal `none` port has not yet
  run on a Cortex-M core ([#5](https://github.com/sgstreet/rtoskit-gcc/issues/5)).
- C++ has no wide characters, and `std::filesystem` does nothing useful. `std::random_device` reads `getentropy`, which
  fails on a board whose port has no entropy source.
- The multilib set is a subset of GCC's `rmprofile` set: no softfp, Armv8-M Baseline, Armv8.1-M MVE or Cortex-R
  multilibs ([#3](https://github.com/sgstreet/rtoskit-gcc/issues/3)). ARM-state and Armv4/5 targets are not supported.
- The archives are not built by a workflow, so they carry no provenance attestation. Check them against `SHA256SUMS`;
  the tag is signed.

See the [README](https://github.com/sgstreet/rtoskit-gcc#readme) for the multilib table, the specs options and how to
build the toolchains yourself.
